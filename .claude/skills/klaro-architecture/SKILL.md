# klaro-architecture — 아키텍처 골격 설계

요구사항 계약을 받아 "어떻게 구성할지"의 골격을 확정한다.

## 절차

1. **계약 로드** — `_workspace/01_spec-analyst_contract.md`의 "결정 필요 목록"과 불변식 체크리스트를 먼저 본다.

2. **스택 결정** — 각 미확정 항목을 결정하고 근거·트레이드오프를 1~2줄로 남긴다. 기본 권장(팀 확인 필요로 표시):
   - Control Plane 언어: 고동시성·gRPC·낮은 메모리 → **Go** 권장(팀 TS 역량이 크면 NestJS).
   - 로컬 오케스트레이션: 프로덕션 근접(동적 스케일아웃/즉시 회수 재현) → **로컬 K8s(k3s/kind)**; 단순성 우선이면 Compose.
   - 큐: 잡 디스패치+이벤트 → **NATS JetStream**(경량); 과금 이벤트 재처리 강하면 Kafka.
   - 테넌트 격리: 기본 **공용 DB + RLS**, Enterprise는 스키마/DB 분리 옵션.
   - Bedrock: 모델/리전/월 토큰 예산 상한 명시 + **mock 기본**([COST-03]).

3. **모듈 경계** — 서비스별로 하나의 책임 + 인터페이스만 노출. 큰 파일이 생기면 책임 분해 신호.

4. **데이터 모델 → 마이그레이션 초안** — `02-data-model.md`의 테이블·인덱스·RLS 정책을 마이그레이션 순서로 정리(FK 의존 순).

5. **서비스 인터페이스** — REST(클라이언트), gRPC+Protobuf+mTLS(CP↔Worker), WS(실시간 메트릭), 큐(잡/과금 이벤트). 각 경계의 메시지 스키마 요지.

6. **빌드 순서** — 의존 그래프 기반(예: 테넌시/인증 → 프로젝트/도메인 검증 → 잡/워커 → 집계/리포트 → 과금 → 프론트).

## 산출물
`_workspace/02_architect_design.md` (스택 결정 / 모듈 경계 / 데이터 모델·마이그레이션 / 서비스 인터페이스 / 빌드 순서).

## 왜 이렇게 하나
불변식을 아키텍처 경계에 내장하면 빌더가 실수로 우회하기 어렵다(예: 도메인 검증을 잡 생성 서비스의 진입 게이트로 두면 우회 불가). 비용 게이트를 설계에서 막으면 유료 의존이 코드에 스며드는 것을 원천 차단한다.
