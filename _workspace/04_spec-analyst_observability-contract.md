# klaro S3 상시 관측 플랫폼 — 요구사항 계약

**작성** spec-analyst · **버전** v1 · **근거** docs/klaro/00 §2.4·§3, 01 §2.4·§3·§4, 02 §2.5·§3, 03 §2·§3.7, 04 §6, 05 §4.6·§11 (모두 2026-08-23 마커 포함)
**전환 배경** S3(APM)를 배포 리포트(S4) 종속 스냅샷 기능에서 **독립된 상시 관측 제품(Datadog 유사, 최종 목표)**으로 승격. 수집·저장·조회·알림은 부하/리포트 잡 생명주기와 무관하게 **상시** 동작하며, 배포 리포트는 이 플랫폼 데이터의 한 소비자일 뿐이다.
**스택 미확정(architect 몫, 본 계약에서 결정 금지)** 알림 룰 엔진 자체구현 vs Grafana Alerting · Explorer 자체 쿼리 API vs Grafana Explore · org 단위 인증/쿼터·리텐션 스키마 · 관측 과금 축 신설 여부.

---

## 범위

이번 세션 한정. **상시 관측 플랫폼(S3)의 기능 요구사항** — "무엇을(WHAT) + 수용 기준"까지. HOW(스택·스키마·서비스 분리)는 architect로 이관.

포함:
- 잡과 무관하게 상시 동작하는 수집 파이프라인 (OTel SDK → Collector → VictoriaMetrics/Tempo/Loki)
- 조직(org) 단위 관측 API 키 발급·폐기·로테이션 + 수집 쿼터 (기존 project 단위 `ingest_token`에서 승격)
- 알림 룰(threshold) CRUD + 알림 발생·이력
- 메트릭/트레이스/로그 탐색(Explorer) 조회
- 데이터 리텐션/다운샘플링 (플랜별 보존, 기존 `apm_retention_days`와의 관계)
- 대시보드/패널 구성 CRUD (03 §3.7 근거)
- 배포 리포트(S4)의 스냅샷 소비 경계

제외: 프론트엔드 화면 구현, S1(부하)/S2(스캔)/S4(리포트) 내부 로직, SDK 패키지 자체의 자동계측 구현 상세, Billing 계량·과금 계산(발행/소비 지점만 표시), Auth/Org/Project CRUD(전제 의존성).

**ID 추적(신규 접두사 `OBS-*` 제안)**: `[OBS-01]` 상시 수집 파이프라인 · `[OBS-02]` org 관측 API 키/쿼터 · `[OBS-03]` 메트릭 Explorer · `[OBS-04]` 트레이스 Explorer · `[OBS-05]` 로그 Explorer · `[OBS-06]` 알림 룰 CRUD · `[OBS-07]` 알림 발생/이력 · `[OBS-08]` 리텐션/다운샘플링 · `[OBS-09]` 대시보드/패널 · `[OBS-10]` 리포트 스냅샷 소비 경계.
**기존 `APM-01~03`과의 관계(본 계약 판단)**: `APM-01`(저오버헤드 ≤2%)·`APM-02`(near-realtime ≤2초)·`APM-03`(병목 트레이스 ≥3초 span 뷰)는 특정 기능이 아니라 **플랫폼 전역 비기능 요구(NFR)**다. OBS로 **흡수(재번호)하지 않고 그대로 유지**하되, 이제 리포트 스냅샷이 아닌 상시 플랫폼 전체에 적용되는 NFR로 재프레이밍하여 관련 OBS 항목에서 참조한다. 사유: 세 ID가 docs 여러 곳(01·05)에서 교차 참조되어 재번호 시 링크 그래프가 깨진다(CLAUDE.md 문서 지도 원칙). → 하단 `## architect 결정 필요 목록` 및 `## 모호/모순` 참조.

## 요구사항 계약

### O1. 상시 수집 파이프라인 [OBS-01] [APM-01] [APM-02] · MUST
- **설명**: 운영 서비스에 상시 설치된 `klaro-apm` SDK(OTel)가 metrics/traces/logs를 OTel Collector(게이트웨이)로 전송하고, Collector가 메트릭→VictoriaMetrics / 트레이스→Tempo / 로그→Loki로 라우팅한다. 이 파이프라인은 **어떤 부하 테스트/리포트 잡의 생명주기와도 무관하게 24/7 상시 가동**된다.
- **수용 기준**:
  - 실행 중인 klaro 잡이 하나도 없어도 SDK가 보낸 텔레메트리가 수집·저장된다(잡 종료 시 소멸하지 않음 — S1 워커와 정반대 수명).
  - metrics/traces/logs 세 신호가 각각 지정 저장소(VictoriaMetrics/Tempo/Loki)에 도달함이 조회로 확인된다.
  - SDK 전송은 비동기 큐 기반이며 대상 앱 요청 경로를 블로킹하지 않는다([APM-01], 오버헤드 목표 ≤2%).
  - Collector가 스트림을 near-realtime(≤2초)으로 대시보드 구독 채널에 push한다([APM-02]).
- **데이터**: 실측 신호는 TSDB/Tempo/Loki(RDB 미저장). RDB에는 참조 키/에이전트 메타만. `apm_agents`(현행) → org 단위 모델로 승격(O2 참조).
- **API(내부)**: OTLP over gRPC + **mTLS 필수** (SDK↔Collector).

### O2. 조직(org) 단위 관측 API 키 발급·폐기·로테이션 + 수집 쿼터 [OBS-02] · MUST
- **설명**: 현행 project 단위 `apm_agents.ingest_token`을 **조직(org) 단위 관측 API 키**로 승격한다. org 관리자가 수집 API 키를 발급/폐기/로테이션하고, 조직 단위 수집 쿼터(호스트 수·데이터 수집량 등)를 조회한다. 여러 서비스/호스트가 하나의 org 키(또는 org 하위 키)로 텔레메트리를 전송한다.
- **수용 기준**:
  - org 키 발급 → 응답에 키 식별자와 (1회 노출되는) 시크릿·연결된 org_id 포함, 상태 `active`.
  - 키 폐기(revoke)/로테이션 후 구(舊) 키로의 수집이 거부된다.
  - 조직 쿼터 조회 → 현재 활성 호스트 수·기간 내 수집량 대비 플랜 한도 반환.
  - 쿼터 초과 시 수집이 거부 또는 제한되고 관측 가능한 신호(에러/헤더/이력)가 남는다. 초과 시 동작(차단 vs 과금)은 정책 결정 필요 → 모호/모순 참조.
  - 키는 RLS로 스코프된 org에만 귀속되며, 타 org 키로 전송된 데이터는 해당 org 스코프로 격리 저장된다.
- **데이터**: 신규 org 단위 키/쿼터 테이블 필요(스키마는 architect 확정). 현행 `apm_agents(project_id, ingest_token, language, last_seen_at)`는 MVP 스코프 → org 승격 시 마이그레이션 대상. `plans`에 수집 쿼터 축(호스트/데이터량) 신설 여부는 결정 필요.
- **API**: 조직 단위 관측 API 키 발급/폐기/로테이션·쿼터 조회 (03 §3.7 계획 표면; 구체 경로/스키마는 architect).

### O3. 메트릭 탐색(Explorer) 조회 [OBS-03] [APM-02]
- **설명**: 임의 시간 구간·필터(서비스/호스트/라벨)·집계(rate/avg/p95 등)로 메트릭을 질의해 시계열을 반환한다. 특정 잡이 아니라 org의 상시 메트릭 대상.
- **수용 기준**:
  - 시간 구간(from/to)·필터·집계 함수를 파라미터로 받아 시계열 포인트를 반환한다.
  - 원본은 VictoriaMetrics에서 조회하며 RDB에 시계열 원본을 저장하지 않는다(불변식).
  - 조회는 요청자의 org 스코프 데이터로만 제한된다(RLS/키 스코프).
- **데이터**: VictoriaMetrics(원본). RDB는 참조/메타만.
- **API**: 메트릭 Explorer 쿼리 API (03 §3.7; 스키마 architect).

### O4. 트레이스 탐색(Explorer) 조회 [OBS-04] [APM-03]
- **설명**: 트레이스를 서비스·시간 구간·지연 임계로 검색하고, 개별 트레이스를 span 트리(워터폴)로 조회한다. 병목 트레이스([APM-03], 응답 ≥3초)를 느린 DB 쿼리/함수 하이라이트와 함께 표시할 수 있게 데이터를 제공한다.
- **수용 기준**:
  - 시간 구간·서비스·지연(예 ≥3초) 필터로 트레이스 목록을 반환한다.
  - trace id로 span 트리(부모/자식·소요시간)를 반환한다.
  - 조회는 org 스코프로 제한된다.
- **데이터**: Tempo(원본). RDB는 trace id 등 참조 키만.
- **API**: 트레이스 Explorer 쿼리 API (03 §3.7; 기존 `GET /projects/:id/apm/traces`는 MVP 스냅샷 조회 — O10 경계 참조).

### O5. 로그 탐색(Explorer) 조회 [OBS-05]
- **설명**: 로그를 시간 구간·라벨·전문(full-text) 필터로 질의해 반환한다.
- **수용 기준**:
  - 시간 구간·라벨/텍스트 필터로 로그 라인을 페이지네이션하여 반환한다.
  - 원본은 Loki에서 조회하며 RDB에 로그 원본을 저장하지 않는다(불변식).
  - 조회는 org 스코프로 제한된다.
- **데이터**: Loki(원본). RDB 미저장.
- **API**: 로그 Explorer 쿼리 API (03 §3.7; 기존 `GET /projects/:id/apm/logs`는 MVP 스냅샷 — O10 경계 참조).

### O6. 알림 룰(threshold) CRUD [OBS-06]
- **설명**: 관측 신호(메트릭/에러율/지연 등)에 대한 임계치 기반 알림 룰을 생성·조회·수정·삭제한다. 룰은 조건(대상 신호·비교·임계·평가 창)과 대상 채널을 가진다.
- **수용 기준**:
  - 룰 생성 → 조건과 채널이 저장되고 활성/비활성 토글이 가능하다.
  - 룰 목록/상세 조회, 수정, 삭제가 org 스코프 내에서 동작한다.
  - 잘못된 조건(미지원 신호·비교 연산자 등)은 검증 오류(422)로 거부된다.
- **데이터**: 신규 알림 룰 테이블 필요(스키마는 architect). org_id 스코프.
- **API**: 알림 룰 CRUD (03 §3.7; 스키마 architect).
- **주의**: 룰 엔진 자체구현 vs Grafana Alerting 재사용은 architect 결정(HOW). 본 계약은 "룰을 CRUD하고 평가·발동해야 한다"는 WHAT만 확정.

### O7. 알림 발생·이력 [OBS-07]
- **설명**: 활성 룰이 조건을 충족하면 알림을 발생시키고, 발생/해소(resolve) 이력을 기록·조회할 수 있게 한다. 개발 단계 통지 채널은 비용 정책상 MailHog(이메일)/Slack 스텁만 사용.
- **수용 기준**:
  - 룰 조건 충족 시 알림이 발생하고 이력에 (룰·발생 시각·값·상태) 레코드가 남는다.
  - 조건 해소 시 상태가 resolved로 전이되고 이력에 반영된다.
  - 통지 발송은 개발 환경에서 MailHog/Slack 스텁으로 캡처되며 외부 유료 발송을 호출하지 않는다([COST-05] 준수).
  - 이력 조회는 org 스코프로 제한된다.
- **데이터**: 신규 알림 이력 테이블 필요(architect). org_id 스코프.
- **API**: 알림 이력 조회 (03 §3.7; 스키마 architect).

### O8. 데이터 리텐션·다운샘플링 (플랜별 보존) [OBS-08] [BILL-03] · MUST
- **설명**: 플랜별 관측 데이터 보존 기간(Free 24h / Pro 14d / Enterprise 90d)을 적용하고, 경과 데이터는 TSDB/Tempo/Loki 리텐션 정책 + 배치 삭제 잡으로 제거한다. 장기 보존 구간의 메트릭 다운샘플링(해상도 하향) 여부는 결정 필요.
- **수용 기준**:
  - 플랜의 `plans.apm_retention_days`(또는 승격된 보존 정책)를 초과한 데이터는 조회되지 않으며 저장소에서 제거된다.
  - 개발 환경에서도 동일 보존 정책이 적용되되 로컬 디스크 용량만 관리한다(04 §4 근거).
  - 상시 가동(24/7) 특성상 잡 기반 대비 로컬 자원(디스크/메모리) 소요가 커질 수 있어, 저장 증가에 대한 관측 가능한 한도/경보 지점이 존재한다(04 §6 신규 항목).
- **데이터**: `plans.apm_retention_days`(현행) — org 상시 플랫폼 승격 시 신호별(메트릭/트레이스/로그) 개별 보존·다운샘플링 정책으로 확장 여부 결정 필요.
- **API**: (내부 배치) 리텐션/삭제 잡. 사용자 노출 API 여부는 architect.

### O9. 대시보드·패널 구성 CRUD [OBS-09]
- **설명**: 사용자가 관측 신호를 조합한 대시보드(패널 구성)를 만들고 저장·수정·삭제한다.
- **수용 기준**:
  - 대시보드 생성/조회/수정/삭제가 org 스코프 내에서 동작한다.
  - 패널 구성(쿼리·시각화 유형·배치)이 저장·복원된다.
- **데이터**: 신규 대시보드/패널 테이블 필요(architect). org_id 스코프.
- **API**: 대시보드(패널 구성) CRUD (03 §3.7 근거).
- **주의**: 자체 대시보드 vs Grafana 대시보드 재사용은 architect 결정. 최소 범위(팀리드 지시) 밖이나 03 §3.7에 명시되어 계약에 포함 — 마일스톤 편입 시점은 결정 필요(05 §11.6).

### O10. 배포 리포트(S4)의 스냅샷 소비 경계 [OBS-10] [RP-*] · MUST(경계 정의)
- **설명**: 배포 리포트(S4)는 이 상시 플랫폼의 데이터를 **"리포트 생성 시점 기준 특정 시간 구간의 스냅샷"**으로 조회해 소비하는 하나의 소비자다. 리포트는 관측 데이터를 소유·저장하지 않고, 리포트 시점 구간을 Explorer 조회 경로로 읽어 조인한다.
- **수용 기준**:
  - 리포트 생성(S4 `AGGREGATING`) 시 지정된 시간 구간(예: 부하 테스트 실행 구간)의 메트릭/트레이스를 상시 플랫폼에서 조회해 소비한다.
  - 상시 수집/저장/보존은 리포트 생성 여부·성패와 무관하게 계속된다(리포트가 데이터 수명을 좌우하지 않음).
  - 기존 MVP 경로 `GET /projects/:id/apm/{traces,logs}`(project 단위)는 리포트용 스냅샷 조회로 유지되고, 상시 탐색은 O3~O5의 org 단위 Explorer로 분리된다(경계 명확화).
  - S1 부하 워커의 메트릭(잡 수명과 함께 소멸 가능)과 상시 관측 텔레메트리(상시 보존)는 서로 다른 수명·경로임이 데이터 흐름상 구분된다.
- **데이터**: `reports.load_test_id`(현행) 조인 관계 유지. APM 데이터는 참조 조회(소유 아님).
- **API**: S4 리포트 API(기존) ← O3~O5 Explorer 조회를 소비. 신규 API 없음(경계 계약).

## 불변식 체크리스트 (MUST)

- **RLS 멀티테넌시**: org 관측 API 키·알림 룰·알림 이력·대시보드 등 신규 org_id 스코프 테이블 전체에 RLS 정책, 요청마다 `SET app.current_org = <uuid>`. 수집 키는 org에 귀속되고 텔레메트리는 org 스코프로 격리 저장. 크로스테넌트 조회/수집 불가. (02 §3, 01 §3)
- **내부 mTLS**: SDK↔Collector는 OTLP over gRPC + **mTLS 필수**. 상시 파이프라인 전 구간에 적용. (00 §2.4, 01 §2.4·§4)
- **시계열 RDB 분리**: 메트릭/트레이스/로그 원본은 VictoriaMetrics/Tempo/Loki, PostgreSQL은 참조 키·에이전트/키 메타만 보관. Explorer 조회는 각 저장소를 원본으로 한다. (02 서두·§2.5, 00 §3)
- **워커 idle=0과의 구분(주의)**: 이 플랫폼은 잡 워커가 아니라 **상시 가동** 컴포넌트다. "잡 종료 시 회수" 불변식은 S1 워커에만 적용되며, 관측 파이프라인은 상시 유지가 정상이다(상반 수명 — 혼동 금지). (00 §2.4)
- **비용 게이트 [COST-05]**: 통지·수집·저장 전 구간을 셀프호스팅 OSS(VictoriaMetrics/Tempo/Loki/MailHog/Slack 스텁)로 유지. Bedrock 외 유료 외부 서비스 호출 추가 금지. (04 §6, CLAUDE.md 비용 정책)
- **보존 자동화 [BILL-03]**: 플랜별 보존일 초과 데이터는 리텐션 정책 + 배치 삭제로 제거(개발/프로덕션 동일 정책). (02 §3, 04 §4)
- **저오버헤드/실시간 NFR [APM-01][APM-02][APM-03]**: 수집 오버헤드 ≤2%, 대시보드 push ≤2초, 병목 트레이스 ≥3초 span 뷰 — 플랫폼 전역 NFR로 유지. (01 §2.4)
- **감사 로그**: 관측 API 키 발급/폐기/로테이션, 알림 룰 변경 등 권한·설정 변경 이벤트를 audit_logs에 기록(SOC2 대비). (01 §4)

## architect 결정 필요 목록

확정 사항(셀프호스팅 스택 VictoriaMetrics/Tempo/Loki, OTLP+mTLS, RLS)은 제외. 아래는 상시 관측 범위에 걸린 미확정 설계 결정(HOW).

1. **알림 룰 엔진**: 자체 구현 vs Grafana Alerting 재사용 (00 §2.4·01 §2.4 병기). 평가 주기·상태 관리·통지 라우팅 방식.
2. **Explorer 조회 계층**: 자체 쿼리 API vs Grafana Explore 재사용 (00 §2.4). 쿼리 언어 노출 범위(PromQL/LogQL/TraceQL passthrough vs 추상화).
3. **대시보드 구현**: 자체 패널 CRUD vs Grafana 대시보드 임베드/프록시.
4. **org 단위 인증/쿼터 모델**: org 키 ↔ 기존 project `apm_agents.ingest_token` 마이그레이션 경로, org 하위 키(서비스/호스트별) 발급 계층 여부, 쿼터 산정 축(호스트 수 vs 수집 GB vs 활성 시리즈).
5. **리텐션/다운샘플링 스키마**: 신호별(메트릭/트레이스/로그) 개별 보존 vs 단일 `apm_retention_days` 유지, 장기 구간 메트릭 다운샘플링 해상도·정책.
6. **관측 과금 축 신설 여부** (04 §6 신규): 호스트 수·수집량(GB)·리텐션 기준 과금을 기존 VU-Minutes와 병행할지. + 상시 가동 로컬 자원(디스크/메모리) 상한·경보 기준을 §4 FinOps에 추가할지.
7. **near-realtime push 경로**: Collector → Control Plane WS push 방식(01 §2.4)과 Explorer 조회 경로의 관계(스트리밍 구독 vs 폴링).
8. **테넌트 격리 수준**: 공용 저장소 + org 라벨 스코프 vs org별 저장소/네임스페이스 분리(Enterprise), 각 TSDB/Tempo/Loki의 멀티테넌시 방식.
9. **APM-01~03 재프레이밍 승인**: 본 계약은 세 ID를 재번호 없이 플랫폼 전역 NFR로 유지 권고. docs 링크 그래프 보존이 사유. architect/문서 담당 확인 필요(모호/모순 1 참조).

## 모호/모순

1. **APM-01~03 vs OBS-* 경계**: 사용자 요청이 "기존 APM-01~03과의 관계 명시"를 요구. 본 계약은 세 ID를 OBS로 흡수하지 않고 NFR로 유지 권고(docs 여러 곳 교차 참조·재번호 시 링크 파손). 최종 채택은 architect/문서 담당 승인 필요.
2. **`apm_agents` project→org 승격 처리**: 02 §2.5 마커는 "org 단위 API 키 + 쿼터 모델 필요"라 하나 기존 project 단위 `ingest_token`의 마이그레이션/공존 여부(project 하위 키 유지 vs org 전면 대체)는 근거 없음.
3. **쿼터 초과 동작**: O2에서 수집 쿼터 초과 시 차단인지, 초과 수집 허용 후 과금인지 정책 미정(04 §6은 과금 축 "신설 여부"만 질문). VU-Minutes 초과 정책([BILL-02])과의 정합성도 확인 필요.
4. **MVP 스냅샷 API의 존치**: 03 §2의 `GET/POST /projects/:id/apm/*`(project 단위)와 §3.7의 org 단위 Explorer가 **공존**하는지(리포트용 유지 + 상시용 신설) 아니면 대체인지 문서가 "MVP 스코프"라고만 표기. O10은 공존을 전제로 작성 — 확인 필요.
5. **알림 통지 채널 계약**: 개발 MailHog/Slack 스텁만 확정. 상시 관측 알림의 채널 종류(웹훅·이메일·인앱)·페이로드 최소 스키마는 근거 얕음(S1 서킷 브레이커 알림 스텁과 공유하는지도 불명확).
6. **다운샘플링 요구 근거**: 사용자 요청에 "다운샘플링"이 있으나 docs 원문은 리텐션(보존·삭제)만 명시하고 다운샘플링(해상도 하향 장기보존)은 명시 근거 없음. Datadog 유사 목표에서 유추한 항목 — 요구 확정 필요.
7. **대시보드 범위**: 03 §3.7에 대시보드 CRUD가 있으나 팀리드 최소 범위·05 §11.6은 "어느 마일스톤까지 만들지" 미정. O9를 어느 릴리스에 포함할지 결정 필요.
8. **SDK 배포·버전관리**: 00 §2.4는 "SDK 상시 설치 전제 배포·버전관리 전략 필요"라 하나, 이는 수집 파이프라인 요구(O1)의 전제일 뿐 본 세션 계약 범위 밖. SDK 패키지 릴리스 전략은 별도 스코프로 분리 권고.
